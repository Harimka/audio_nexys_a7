# Полный контекст проекта и передача другим агентам

Актуализировано: 2026-10-24, Europe/Moscow. Это сводка технического разговора и наблюдений, а не дословная стенограмма. При противоречии со старыми планами приоритет имеют последнее прямое поручение пользователя и этот документ. Для плана действий см. [ROADMAP.md](ROADMAP.md), для формата команд — [MIDI_PROTOCOL.md](MIDI_PROTOCOL.md).

## 1. Задача, которую хочет команда

Сделать музыкальный инструмент на Digilent Nexys A7-100T: человек играет на Arturia MicroLab mk3, плата получает команды клавиш, определяет ноту, генерирует звук методом таблично-волнового синтеза и выводит его в наушники через MONO AUDIO OUT. Синтез происходит на FPGA.

Предпочтительная конечная физическая схема: **MicroLab (USB-C) → USB HOST платы (USB-A) → логика FPGA → MONO AUDIO OUT → наушники**. Ноутбук нужен только для разработки/прошивки, не для игры. Это желание пользователя, а не уже достигнутая функциональность.

Ноутбук позднее разрешили использовать для диагностического эксперимента: подключить MicroLab, увидеть USB/MIDI-устройство и реальные нажатия. Эксперимент выполнен пользователем. Это не означает принятие ноутбука как части конечной системы. Пользователь предложил написать программный мост и исследовать именно соединение клавиатуры с платой. Не подменять желаемое прямое соединение ноутбучным молча.

Исходное название задания/README — музыкальный плеер. Последнее выбранное пользователем направление — интерактивный wavetable-синтезатор. Соответствие этого направления всем критериям хакатона ещё нужно проверить; подробной шкалы нет.

## 3. Что действительно наблюдалось на реальной аппаратуре

### FPGA programming

На фото Vivado Hardware Manager устройство `xc7a100t_0` имеет статус `Programmed`, bitstream `audio_nexys_a7.bit`; в Tcl Console — `End of startup status: HIGH` и информационное сообщение об отсутствии поддерживаемых debug cores. Это подтверждает загрузку прежнего архивного bitstream, а не работу нового MIDI RTL. `There are no debug cores` не является ошибкой прошивки. На плате светится DONE, индикатор отображает состояние демо.

Факт слышимого звука именно от новой MIDI-версии **не подтверждён**. Подключение наушников не является подтверждением слышимого сигнала. Изображения индикаторов не позволяют заявить, что MIDI-команды получены.

### MicroLab → Linux

Пользователь переставил USB MicroLab в Ubuntu-ноутбук и прислал вывод:

```text
lsusb:
ID 1c75:020c Arturia MicroLab mk3

aseqdump -l:
20:0  MicroLab mk3  MicroLab mk3
```

При `aseqdump -p 20:0` на фото видны:

```text
channel 0: Note on  48 velocity 36
channel 0: Note off 48 velocity 57
channel 0: Note on  50 velocity 40
channel 0: Note off 50 velocity 51
channel 0: Note on  52 velocity 63
channel 0: Note off 52 velocity 37
channel 0: Note on  55 velocity 54
channel 0: Note off 55 velocity 57
channel 0: Note on  53 velocity 34
channel 0: Note off 53 velocity 56
channel 0: Note on  52 velocity 68
channel 0: Note off 52 velocity 72
```

Также видны CC1 (значения 27/28) и Pitch Bend с отрицательными значениями и возвратом к нулю. Это проверка MIDI-событий, интерпретированных ALSA, не захват сырых USB-пакетов. Порт `20:0` может измениться при переподключении.

Выводы: клавиатура, USB-кабель и приём MIDI на этом ноутбуке работали в показанном эксперименте. MIDI Note Off может иметь ненулевую release velocity — не путать её с новым нажатием. Канал ALSA 0 соответствует привычному пользовательскому MIDI-каналу 1. `lsusb` и наличие MIDI-порта **не исключают** дополнительных USB-интерфейсов устройства; полный descriptor dump не получен.

## 4. Текущее программное состояние

### Исходное демо

DDS одиночных нот, FIFO, PWM mono output, кнопки/переключатели/семисегментный индикатор, статический VGA 800×600. Это не готовое воспроизведение SD/WAV/MP3 и не USB-MIDI host. AUD_PWM должен оставаться open drain 0/Z. Частота audio clock по проекту 49,15865 МГц; темп PWM-сэмплов примерно 48006,49 Гц.

Исходные органы управления: BTNC переключает play; BTNU/BTND громкость; BTNL/BTNR ноты; SW[2:0] октава. В расширенном top SW15 выбирает MIDI voice (1) либо исходное демо (0). Полная пошаговая история — BOARD_BRINGUP.md. Не выдавать исходный bitstream за сборку новых исходников.

### Сделано помощником

- UART RX 115200 8-N-1, вход C4 (`UART_TXD_IN`) через FTDI PROG/UART.
- `midi_note_decoder.sv`: сырые MIDI-байты → события on/channel/note/velocity; running status, Note On velocity=0, пропуск real-time байтов, отмена сборки через другие статусы.
- `midi_note_state.sv`: один голос, последнее нажатие выигрывает; выключение только при совпадении ноты и канала. Ранее удерживаемая нота автоматически не восстанавливается.
- `midi_uart_receiver.sv`: обёртка UART → общий decoder/state; исправлена путаница Note Off одинакового pitch на разных каналах.
- `midi_wavetable.sv`: синус на 256 точек, 32-битная фаза, таблица 128 MIDI-нот, velocity→амплитуда. Пока один тембр и один голос, без ADSR/sustain/pitch bend.
- `usb_midi_note_decoder.sv`: принимает уже извлечённый host-ом USB-MIDI 1.0 Event Packet (32 бита), CIN 8/9, выбранный virtual cable, valid/ready, проверки пакетов. Это **декодер payload**, не реализация физического USB host.
- `usb_midi_voice.sv`: payload decoder → voice state → wavetable. Отдельный интеграционный модуль; не подключён к физическому J5 в board top.
- `tools/midi_uart_bridge.py`: необязательный стендовый ноутбучный мост USB-MIDI → USB-UART; пересылает Note On/Off, а не PCM-аудио. Сценарий с реальным ноутбуком и новой FPGA-версией ещё не проверен целиком.
- Новые tests/midi, baseline audit, инструкции и передача контекста.

Формат: команда `90 30 24` → note=48, velocity=36, channel=0; `80 30 39` → отпускание. USB-MIDI payload для первого примера: байты `09 90 30 24`, шина `32'h24309009`. Формат битов/латентность/handshake — MIDI_PROTOCOL.md. Не подавать сырые USB D+/D− на byte decoder.

## 5. Проверки и их пределы

Последний прогон после изменения RTL: `python3 tests/audit/run_audit.py .` прошёл в Icarus. Проверены UART note events, реальные значения с фото, running status, канал, SysEx exclusion, USB packet packing/backpressure/malformed packets, 4096 событий по 128 нотам × 16 каналам × on/off, payload→wavetable, A4 около 440 Гц в шкале принятых сэмплов, velocity scaling, остановка генератора при backpressure и тишина после Note Off/reset. Элаборированы board top, simulation top и исходный TB с port-only clock stub. `git diff --check` пройден.

Baseline-тесты специально воспроизводят известные дефекты reset при потере PLL lock и смещения VGA VS. Их зелёный результат не означает исправления дефектов. Clock stub не моделирует MMCM. Нет Vivado synthesis/implementation/timing/CDC sign-off новой версии; нет подтверждённого физического USB host, PIC24 firmware или слышимого MIDI-звука на плате.

## 6. Потенциальное ограничение USB HOST и где помощник мог ошибиться

**Не представлять невозможность прямого подключения на конкретном экземпляре как измеренный факт.** По документации стандартной Nexys A7 J5 подключён к PIC24, который штатно преобразует Boot HID клавиатуру/мышь в PS/2 для FPGA. В схеме USB-линии идут в PIC24, PS/2 — в FPGA. Это сильное основание ожидать проблему USB-MIDI, но фактическая firmware PIC24 учебной платы не считана и её поведение с MicroLab не измерено.

Возможные ошибки/неизвестные, которые должен перепроверить следующий агент:

1. **Firmware конкретной платы.** Она может отличаться от заводской; пользователь этого не знает. Не считать отсутствие сведений доказательством отсутствия модификации. В ZIP специальной PIC firmware не найдено; это не доказывает, что её нет на железе или у организаторов.
2. **Дополнительные интерфейсы MicroLab.** Проверен MIDI-порт, но не полный `lsusb -v`. Документация не заявляет Boot HID режим; отсутствие такого режима на конкретном устройстве пока не проверено дескрипторами. Наличие фортепианных клавиш само по себе не определяет USB class.
3. **Ревизия/разводка платы.** Фото согласуется с Nexys A7-100T, но применимость каждой страницы reference schematic и отсутствие аппаратных переделок нужно подтвердить на стенде. Не путать разъём J5 USB HOST и J6 PROG/UART.
4. **Материалы организаторов.** Могут быть специальная firmware, переходник, допустимый notebook bridge или иная предусмотренная схема. Уверенность пользователя, что хакатон предполагает работу клавиатуры, — повод проверить материалы, а не доказательство протокола. Подробного ТЗ нет.
5. **Изменяемость firmware.** Исторический ответ Digilent 2020 года о закрытой PIC firmware не устанавливает её вечную недоступность и не доказывает отсутствие современных альтернатив. Собственная PIC firmware технически возможна как направление, но готовой совместимой сборки и процедуры восстановления здесь нет.
6. **Оценка помощника.** Ранее прозвучали слишком категоричные «на вашем комплекте нельзя» и «единственные варианты». Корректная текущая оценка: штатная документированная схема, вероятно, не передаёт USB-MIDI; прямой путь в данном проекте не реализован/не подтверждён, нужны проверки конкретного экземпляра. Это не обещание, что изменение только RTL обязательно поможет.
7. **Физическая граница не исчезает.** При стандартной разводке RTL FPGA не получает напрямую D+/D− J5; числовой декодер или таблица частот не заменяют enumeration/host. Если проверки подтвердят стандартную firmware/интерфейсы, понадобится изменить host-часть, добавить оборудование или отдельно согласовать временный ноутбук.

Источники и ветви продолжения: [DIRECT_USB_MIDI.md](DIRECT_USB_MIDI.md). Прямой тракт пока не объявлять ни работающим, ни окончательно невозможным на конкретном учебном экземпляре.

## 7. Как проверить неизвестные без подмены цели

- На Linux с MicroLab: сохранить текст `lsusb -v -d 1c75:020c` (при необходимости с sudo); изучить каждый интерфейс class/subclass/protocol, endpoints и USB-MIDI descriptors. Перед публикацией удалить serial strings и другую личную информацию. Не считать ALSA-порт descriptor dump-ом.
- Для платы: подтвердить маркировку/revision, подключения J5/J6 и наличие исходников/описания firmware у организаторов. Сначала изучать предоставленные документы; не отправлять сообщения организаторам от лица пользователя без прямого поручения.
- Если есть разрешённый способ наблюдать PS/2 F4/B2: проверить события при USB HID клавиатуре и при MicroLab, желательно логическим анализатором/осциллографом либо разрешённой RTL-диагностикой на LED/UART. Это будущая проверка, оборудования для неё не подтверждено. Не добавлять запрещённый ILA IP. Отсутствие событий само по себе ещё не определяет причину (питание/кабель/firmware/протокол).
- Если обнаружен поток из PIC24: установить его формат/скорость/электрический интерфейс по измерениям и адаптировать декодер. Не называть его MIDI UART без доказательств.
- Диагностический ноутбучный мост допустим как эксперимент для отделения ошибок аудиотракта от USB; он требует новой сборки FPGA и согласованного подключения. Не менять целевую архитектуру из-за успешного эксперимента без решения команды.
- Не прошивать PIC24 и не менять hardware наугад: программирование другого контроллера не покрывается уже выполненной прошивкой FPGA.

## 8. Ограничения задания и правила передачи

MicroBlaze и Block Design запрещены; допустимые Vivado IP — Clocking Wizard, Block Memory Generator, Distributed Memory Generator, MIG, AXI XBAR. Сторонний открытый код разрешён с лицензиями/атрибуцией; источники должны быть раскрыты эксперту и в презентации. Использование ИИ разрешено, понимание команды влияет на оценку. Максимумы: звук 45, VGA 25, периферия 20, презентация 10; первые три умножаются на K1/K2/K3. Подбаллы и значения K неизвестны.

Срок, полный критерий оценки, обязательность SD/MP3/WAV, полифонии и конкретной VGA-визуализации не установлены. Не придумывать их. Источник ограничений — слайды пользователя; требования к архитектуре — прямые сообщения пользователя. Публикация исходников и контекста в GitHub разрешена пользователем; это не разрешение коммитить личные фото/коды или писать третьим лицам.

## 9. Ошибки направления, которые не надо повторять

- Помощник первоначально внедрил ноутбучный мост как практическое решение, хотя пользователь хотел ноутбук только для прошивки. Мост сохранён как стендовый инструмент; он не закрывает конечную задачу.
- Не объяснять снова и снова теорию USB вместо следующего проверяемого шага. Показывать конкретное наблюдение, тест и его границы.
- Не путать числовой MIDI decoder, UART receiver и полноценный USB host: это разные этапы.
- Не выдавать unit tests за проверку платы; `Programmed` — за слышимый звук; `aseqdump` — за работу прямого соединения.
- Не спрашивать пользователя, какая PIC firmware стоит: он уже сказал, что не знает и предоставил все имеющиеся данные. Технический ответ надо искать в артефактах/измерениях.
